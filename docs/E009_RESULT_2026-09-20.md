# E-009-R1 Result — First Claim-Bearing Aeye Execution Receipt

Status: `observed` local result; `supported` against the preregistered R1 acceptance tests  
Date: 2026-09-20  
Scope: one public, synthetic, finite-field transformer-shaped causal block  
Preregistration: `sha256:f47422817c023655d8daeae53f3ad69288b08e2a0be8328e6146bf2ffffef248`

## Result in one sentence

A separately implemented verifier accepted all 13 frozen causal events, including five
coded matrix–vector relations and eight exact state/nonlinear/decode/output relations,
while all eight preregistered single-mutation controls were rejected; this supports the
toy `EXECUTION` and declared finite-field `SEMANTICS` coordinates, not Pearl `WORK`, real
hardware fidelity, production efficiency, or `DEMAND`.

## Claim vector

| Coordinate | R1 result | Assurance and exact scope |
|---|---|---|
| `WORK` | `unknown` | Synthetic clean-operand roots only. No Pearl certificate, native Pearl relation, mining event, or work-security test was generated or verified. |
| `EXECUTION` | `satisfied` | `sampled`; 13/13 events in the frozen R1 universe. Five linear events use 16 coded checks each; eight boundary events are replayed exactly. Conditional on the stated code, Fiat–Shamir, binding, grinding, hash, and verifier-correctness assumptions. |
| `SEMANTICS` | `satisfied` | `hybrid`; exactly the declared prime-field, centered-decode, hard-attention semantics for 13/13 events. No softmax, floating point, GPU, compiler, kernel, or physical-device mapping. |
| `DEMAND` | `unsupported` | The operator authorized the research run, but no qualifying signed independent request or economic event is represented. |

There is no global “verified inference” result. The vector above is the result.

## Frozen relation

R1 uses the prime

\[
p=2^{61}-1=2305843009213693951.
\]

The model is deliberately small: `d_model=4`, `d_key=3`, `d_value=4`,
`d_hidden=5`, and a six-token vocabulary. It is a transformer-shaped causal block with
one initial KV-cache row and deterministic hard attention. It is not an ordinary
softmax transformer or a language model.

The complete event universe was fixed before execution:

1. request input;
2. query, key, and value linear maps;
3. cache append;
4. attention-score computation and hard selection;
5. residual addition;
6. MLP linear map and centered ReLU;
7. logits linear map, argmax, and output emission.

In event identifiers this is 13 events: five coded-linear and eight exact relations. The
execution selects the newly appended cache row, carries both negative and positive values
through the MLP/ReLU boundary, and emits a unique token: ID `3`, `iris`.

The clean input and `Wq` roots are exposed identically by the synthetic WORK object and
the execution audit. That equality is an observed coupling invariant. The WORK-side object
contains no native Pearl proof, so equality cannot upgrade `WORK` from `unknown`.

## Commitment and challenge order

R1 fixes the request, model, execution profile, and unsupported-demand object, then derives

\[
I=H_F(\texttt{aeye/intent/v0},r_R,r_M,r_E,n,f),
\qquad
J=H_F(\texttt{aeye/job/v0},I,r_D).
\]

After execution it commits the complete trace and output:

\[
r_\sigma=H_F(\texttt{aeye/execution-subject/v0},J,r_T,r_Y).
\]

Only then does it derive each public audit challenge from `subject_root`, event ID, and
repetition under `aeye/e009/coded-mvm-challenge/v0`. The retained timeline is
intent → authorization record → job → subject → challenge → receipt. The authorization
record is run provenance, not a `DEMAND` proof.

## Coded-linear result

For each linear event with output dimension `m`, R1 fixes a Reed–Solomon/Vandermonde MDS
generator over evaluation points `1..N`, with `N=2m`, and authenticates

\[
Q=G^\top M.
\]

Each of 16 repetitions samples four distinct positions and nonzero field coefficients,
then checks

\[
(e^\top Q)x=e^\top G^\top y.
\]

All 80 retained equations accepted in both implementations. For relative code distance
`δ`, sparsity `t=4`, repetitions `ℓ=16`, and fixed MDS generator, the preregistered
per-relation bound is

\[
\epsilon_i\leq
\left((1-\delta_i)^t+\frac{1}{p-1}\right)^\ell.
\]

The five-relation union bound recomputes to approximately

\[
\epsilon_{lin}\leq 4.98536\times10^{-25}<2^{-80.73}.
\]

This number is conditional. It does not include SHA-256 collision failure, Fiat–Shamir
random-oracle loss, subject grinding, implementation bugs, parser bugs, or any Pearl
work-security term. It is not a complete end-to-end security level.

## Complete toy cost surface

Environment: CPython 3.14.2, macOS 14.4, arm64. Provider measurements use 100 warmups and
1,000 repetitions. Verifier measurements use 100 warmups and 250 repetitions. Timings use
`time.perf_counter_ns`. These are local Python microbenchmarks, not serving results.

| Operation | Median | p95 | Interpretation |
|---|---:|---:|---|
| Identical no-Aeye causal-block execution | 29.458 µs | 31.541 µs | Frozen computation baseline |
| Offline preprocessing for all five matrices | 167.334 µs | 175.042 µs | Reported separately; not hidden |
| Online execution, trace, and final subject | 112.041 µs | 119.000 µs | About 3.80× the toy execution baseline |
| Post-subject challenge plus all coded responses | 1,461.354 µs | 1,567.292 µs | About 49.61× the toy baseline; the preregistered R1 timing combines both parties |
| Independent relation replay | 1,940.771 µs | 2,131.667 µs | About 65.88× the toy baseline; excludes schema parsing and disk I/O |

The canonical baseline output is 222 bytes. The provider transfer bundle—trace, output,
synthetic WORK object, audit, and receipt—is 85,584 bytes, about 385.5× the baseline output.
All retained R1 JSON artifacts after appraisal occupy 102,048 bytes; the frozen input is an
additional 6,271 bytes.

These ratios are evidence against claiming practical efficiency. Tiny Python workloads
are dominated by hashing, JSON, and challenge bookkeeping; they cannot predict GPU-scale
overhead in either direction.

| Audit JSON serialization | 235.083 µs | 257.167 µs |
| Audit JSON parsing | 236.354 µs | 256.208 µs |

The isolated medians should not be added and treated as a reconciliation of the combined
R1 timing: each operation was measured in a separate loop. Canonical JSON contains 15,761

sizes, not a measured network protocol. Transport, protocol framing, retransmission,
availability, filesystem and replication overhead, recovery, and production privacy cost
remain unmeasured. R1 implements no privacy mechanism and discloses its public toy model,
inputs, intermediates, and output.

## Independence and replay

The verifier does not import the provider generator or the earlier coded-MVM demonstrator.
It independently implements canonical commitments, finite-field operations, MDS
preprocessing, challenge expansion, coded equations, exact event semantics, and coordinate
policy. This is useful code-path diversity.

It is not independent human authorship, organizational control, a formal verification, a
security audit, or peer review. The verifier still runs in the same repository, on the
same machine, under the same research process.

Replay:

```bash
python3 experiments/e-009/independent_verify.py
python3 scripts/validate.py
python3 -m unittest discover -s tests -v
```

Expected high-level outcome:

```text
E-009 independent replay: ACCEPT
coordinates: DEMAND=unsupported, EXECUTION=satisfied, SEMANTICS=satisfied, WORK=unknown
known-bad controls: 8/8 rejected
```

## What R1 establishes

`observed`:

- the Aeye subject construction can bind one complete, explicitly denominated causal
  execution rather than only place identifiers beside a transcript;
- a synthetic WORK-side clean-operand pair and an execution relation can share identical
  native root fields without upgrading the WORK claim;
- coded checks can coexist with exact cache, nonlinear, decode, and output checks under one
  subject and one result vector;
- the retained implementation catches all eight preregistered substitutions;
- a second code path can replay the receipt from retained public bytes.

`derived`:

- R1 is a constructive witness that the proposed `R_X(subject,h_A,h_B)` interface is not
  merely prose;
- the result closes the former “no execution backend at all” blocker for one toy relation;
- the four-coordinate calculus remains useful even if Pearl is replaced, because the
  execution and semantic relations do not depend on one work protocol.

## What R1 does not establish

- no native Pearl certificate or assumption was tested;
- no clean root was taken from Pearl certificate-v3 or proposed certificate-v4;
- no version-specific Pearl noise, quantization, correction, ticket, or jackpot bridge was
  implemented;
- no ordinary attention, normalization, RoPE, batching, speculative decoding, cache reuse,
  retry, or concurrent scheduling was covered;
- no FP8, INT, GPU, compiler, kernel, energy, physical-work, or device-origin claim exists;
- no privacy mechanism exists; the toy trace and model are public;
- no external challenge beacon, anti-grinding reduction, formal proof, or independent
  security review exists;
- no production performance advantage exists; R1 is expensive relative to its toy
  baseline;
- no real request authorization, payment, utility, or non-circular demand was shown.

## Scientific verdict after R1

The status advances from **empirical core entirely unproven** to **first claim-bearing toy
result supported**. It remains silent on native Pearl integration, comparative system
value, deployment readiness, and adoption.

The strongest defensible statement is:

> Aeye now has a reproducible witness for a complete toy work-to-execution coupling
> interface: the execution side binds the same clean operand roots into a committed causal
> path and output, preserves separate claim coordinates, and rejects eight targeted
> substitutions under an explicit conditional soundness model.

The most important negative result is equally useful: authenticating `Q=G^T M` by
recomputing it makes the verifier touch the full matrix, while the public audit is large
and its Fiat–Shamir transform remains grinding-conditional. Those are the next load-bearing
problems, not presentation details.

## Highest-value next construction

The next frontier should be an **authenticated-preprocessing execution layer**, independent
of Pearl at its core and compatible with Pearl through an adapter:

1. prove once that a committed preprocessing root `r_Q` represents `Q=G^T M` for the exact
   committed model/layout root, then amortize that setup over many requests;
2. bind an unpredictable external challenge or a formally analyzed Fiat–Shamir transform
   to the final subject, with explicit query/grinding loss;
3. aggregate many token-row checks without losing per-request membership and cache lineage;
4. replace hard attention with a frozen quantized attention/normalization profile and
   explicit lookup or sumcheck relations;
5. implement a versioned Pearl adapter that consumes actual native `h_A,h_B` and proves the
   clean-to-noised/quantized bridge without changing Pearl's accepted work statement;
6. compare total provider, challenger/client, verifier, bytes, storage, setup amortization,
   and privacy cost against a named complete proof baseline on the identical workload;
7. obtain review from a cryptographer and a Pearl engineer before making comparative or
   deployment claims.

If authenticated preprocessing cannot be amortized, native roots cannot be exposed without
duplicating dominant work, or the bridge destroys privacy or serving economics, the Pearl
coupling should be stopped or reframed. The independent Aeye evidence calculus would remain
valuable even under that pivot.
